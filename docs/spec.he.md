# איפיון מערכת: TG Session Gateway

שער סשנים לבוטי Telegram Bot API.  
מסמך דרישות ואפיון — לא מדריך הטמעה.

---

## 1. מטרת המערכת

שירות תשתית ארוך־חיים שמחזיק את החיבור לטלגרם עבור מספר בוטים במקביל.

האפליקציות מדברות עם טלגרם רק דרך השער. פריסת גרסה של אפליקציה לא מנתקת את הסשן מטלגרם ולא מחייבת reconnect.

השער אוכף את מגבלות ה־Bot API כדי למנוע 429 שמשביתים את הבוט זמנית לכל המשתמשים.

---

## 2. בעיות שהמערכת פותרת

| בעיה | תוצאה היום | יעד |
|---|---|---|
| `getUpdates` שייך לאפליקציה | כל deploy יוצר Conflict / reconnect / דיליי | בעלות על החיבור אצל השער בלבד |
| טוקן אחד, כמה תהליכים | נפילות אקראיות | poller יחיד לכל טוקן |
| שידור / מענה מהיר מדי | 429, ואז הבוט דומם לכולם | חסימה או תור לפי דליים רשמיים |
| השער יושב ב־compose של הפרויקט | `compose down` מפיל גם את הסשן | מחזור חיים נפרד לחלוטין |

---

## 3. היקף

### בפנים

- ריבוי בוטים (טוקנים) בתהליך אחד
- בעלות בלעדית על קבלת עדכונים מטלגרם לכל טוקן
- תור עדכונים פנימי ששורד ניתוק של האפליקציה
- פרוקסי יוצא תואם Bot API
- הגבלת קצב לפי חוקי FAQ, כולל לפי משתמש/צ׳אט
- ממשק ניהול פנימי
- חיבור מכל פרויקט באמצעות החלפת base URL בלבד

### בחוץ

- לוגיקת בוט, FSM, LLM, DB משתמשים
- סשני משתמש MTProto (Telethon / Pyrogram / tdata)
- פאנל ווב עשיר
- אשכול replicas שחולקים אותו טוקן
- פרסום לאינטרנט
- ניהול מתוך ה־compose של הפרויקטים הצרכניים

---

## 4. עקרונות מחייבים

1. **שני מחזורי חיים.** השער לא שייך לשום פרויקט בוט. פריסה/כיבוי של פרויקט צרכן אינם משפיעים על תהליך השער, הרשת שלו או ה־volume שלו.
2. **טוקן אחד = בעלים אחד.** אסור ששני pollers בעולם יריצו `getUpdates` על אותו טוקן.
3. **האפליקציה לא מדברת עם `api.telegram.org`.** כל קריאה עוברת בשער.
4. **השער לא מייצר 429 אצל טלגרם במכוון.** חריגה נעצרת או מושהית פנימית.
5. **מקור אמת יחיד לקצב.** לא מחייבים limiter כפול באפליקציה.
6. **Webhook ו־getUpdates מול טלגרם הם XOR.** השער בוחר אחד. האפליקציה לא קובעת את זה מול טלגרם.

## 5. בידוד תפעולי

### 5.1 זהות תשתית

| פריט | ערך |
|---|---|
| מיקום | `/opt/tg-gateway` (או נתיב שקול שאינו בתוך ריפו צרכן) |
| שם פרויקט Docker | `tg-gateway` בלבד |
| שם קונטיינר | `tg-gateway` |
| רשת | `tg-gateway-net`, חיצונית, נוצרת פעם אחת |
| פורט ניהול ו־API | `127.0.0.1:8080` בלבד, או פורט פנימי ברשת Docker |
| volume | בלעדי לשער, מחוץ לתיקיות הפרויקטים |
| label חובה | `tg.gateway=true` |

### 5.2 איסורים

- הופעת שירות השער ב־compose של פרויקט צרכן
- `depends_on` מהצרכן אל השער
- אותו `COMPOSE_PROJECT_NAME` כמו צרכן
- סקריפטי ניקוי/Watchtower שפועלים על כל הקונטיינרים בלי סינון label
- `docker compose down` ברמת מכונה שכולל את השער

### 5.3 חוזה מול פרויקט צרכן

הצרכן רשאי רק:

- להצטרף לרשת `tg-gateway-net` כ־`external: true`
- להגדיר base URL אל השער
- להעביר טוקן / alias

הצרכן אינו מקים, לא מכבה ולא מעדכן את השער.

עדכון השער הוא פעולה נפרדת, מבוקרת, עם drain של תורים.

## 6. ארכיטקטורה לוגית

```
Telegram Bot API
        │
        │  חיבור יחיד לכל טוקן
        ▼
┌───────────────────────────────────────────┐
│              TG Session Gateway            │
│                                           │
│  Control plane     Session plane          │
│  ─────────────     ─────────────          │
│  רישום בוטים       poller לכל טוקן        │
│  מצב / מדדים       offset מול טלגרם       │
│                    Update Bus             │
│                                           │
│  Egress plane      Rate Guard             │
│  ────────────      ──────────             │
│  פרוקסי Bot API    דלי גלובלי לבוט        │
│  תור שליחה         דלי לפי משתמש          │
│                    דלי לפי קבוצה          │
│                    pause אחרי 429         │
└───────────────────────────────────────────┘
        │                      │
        ▼                      ▼
   פרויקט A               פרויקט B
   (מתחלף בפריסה)         (מתחלף בפריסה)
```

### 6.1 Session plane

ישות `BotSession` לכל טוקן:

- מזהה יציב (`alias`) + טוקן מוצפן
- מצב: `connecting | live | paused | draining | error`
- poller יחיד או webhook יחיד מול טלגרם
- `telegram_offset` שמור לדיסק
- תור עדכונים פנימי

אחרי attach: השער קורא `deleteWebhook` ואז מתחיל polling, אלא אם הוגדר במפורש מצב webhook מול טלגרם (לא ברירת מחדל).

השער לא קורא `logOut` בשגרה.

### 6.2 Update Bus

- קבלת עדכון מטלגרם → כתיבה לתור + עדכון offset → רק אז ack לטלגרם
- האפליקציה מאשרת offset **פנימי** נפרד
- ניתוק אפליקציה לא משפיע על החיבור לטלגרם
- קיבולת תור מוגדרת לכל בוט; בגלישה: מדיניות `drop_oldest` או `reject_new` (ברירת מחדל: `drop_oldest` עם מדד התראה)

גרסת מוצר 1: צרכן פעיל אחד לכל בוט.  
גרסת מוצר 2 (לא חובה לאיפיון הראשון): כמה צרכנים עם lease.

### 6.3 Egress plane

ממשק תואם Bot API:

```
/tgapi/bot<token>/<method>
/tgapi/bot<token>/getUpdates
/file/bot<token>/<path>
```

חלופה בלי טוקן ב־URL:

```
/bots/<alias>/<method>
Authorization: Bearer <app-secret>
```

התשובה זהה לפורמט טלגרם (`ok`, `result`, `error_code`, `parameters.retry_after`).

כל בקשת כתיבה עוברת Rate Guard לפני יציאה לטלגרם.

### 6.4 כשלים

- קריסה ב־session של בוט A לא מפסיקה בוטים אחרים.
- השער down הוא האירוע היחיד שגורם reconnect לטלגרם. האפליקציות מחכות ל־health; הן לא עוברות ל־`api.telegram.org`.

## 8. הגבלת קצב

מקור נורמטיבי: [Telegram Bots FAQ](https://core.telegram.org/bots/faq), ופרמטר `allow_paid_broadcast` ב־[Bot API](https://core.telegram.org/bots/api).

טלגרם לא מפרסמת מכונת מצבים מלאה. המערכת מממשת את המספרים שכן פורסמו, ומכבדת כל `retry_after` אמיתי כעדיפות עליונה.

### 8.1 דליים

| שם | חוק רשמי | מימוש | מפתח |
|---|---|---|---|
| Per-user / single chat | לא יותר מהודעה אחת לשנייה בצ׳אט בודד; פרץ קצר מותר | 1 טוקן/שנייה, burst 3 | `bot_id + chat_id` בצ׳אט פרטי |
| Per-group | לא יותר מ־20 הודעות לדקה בקבוצה | 20 טוקנים / 60 שניות, burst ≤ 2 | `bot_id + chat_id` ל־group / supergroup / channel |
| Global broadcast | לא יותר מ־כ־30 הודעות לשנייה לכלל הצ׳אטים | 30 טוקנים / שנייה | `bot_id` |
| Paid broadcast | עד 1000/שנייה אם הופעל ב־BotFather; 0.1 Stars לכל הודעה מעל 30 החינמיות; תנאי סף של יתרת Stars ו־MAU | דלי 1000/שנייה רק באישור כפול | `bot_id` |

"לפי משתמש" = דלי הצ׳אט הפרטי. בשיחה פרטית `chat_id` הוא מזהה המשתמש.

### 8.2 כללי אכיפה

1. מתודות כתיבה עם `chat_id` נספרות בדליים (לא רק `sendMessage`: כולל מדיה, forward, copy, edit).
2. מתודות קריאה (`getMe`, `getChat`, …) בדלי גלובלי רך נפרד, לא בדלי המשתמש.
3. `answerCallbackQuery` ו־`answerInlineQuery` במסלול מהיר, מחוץ לדלי השידור.
4. סיווג צ׳אט לפי cache של `getChat`. `chat_id` שלילי אינו פרטי.
5. 429 מטלגרם עם שיוך לצ׳אט → pause לדלי של הצ׳אט ל־`retry_after`.
6. 429 בלי שיוך → pause לכל ה־egress של הבוט ל־`retry_after`.
7. אסור לשלוח שוב לאותו יעד לפני תום ההמתנה.
8. `allow_paid_broadcast` מכבדים רק אם גם בקונפיג הבוט בשער `paid_broadcasts_enabled=true`.
9. המערכת לא שולחת מעבר לתקרה "כדי לבדוק את טלגרם".

### 8.3 התנהגות כשהדלי ריק

מוגדר לכל בוט:

- `queue` (ברירת מחדל): הבקשה ממתינה בתור per-chat. הלקוח מחכה עד timeout מוגדר או מקבל `202` עם מזהה תור.
- `reject`: החזרה מיידית של 429 מלאכותי עם `retry_after` משוער.

יעד איכות: מספר 429 אמיתיים מטלגרם ≈ 0 בפעילות תקינה.

## 9. התנהגות בפריסה

### 9.1 פריסת אפליקציה צרכנית

השער ממשיך `getUpdates`. עדכונים מצטברים בתור הפנימי. האפליקציה החדשה מתחברת ומושכת. אין handshake מול טלגרם ואין Conflict.

### 9.2 פריסת השער

אירוע נדיר. דורש drain, החלפת תהליך, שחזור offset מהדיסק. זה המקרה היחיד של reconnect לטלגרם. הצרכנים רואים חוסר־מוכנות וממתינים.

### 9.3 ניתוק לא מתוכנן של צרכן

הסשן מול טלגרם נשאר `live`. התור גדל עד תקרה. אחרי חיבור מחדש הצרכן ממשיך מ־offset פנימי.

## 10. ממשקים

### 10.1 צרכן — Bot API תואם

הצרכן מחליף את `https://api.telegram.org` ב־base של השער. אין שינוי חוזה מתודות.

מצבי צריכת עדכונים:

| מצב | מי מושך מהשער | שימוש |
|---|---|---|
| Pull | הצרכן קורא `getUpdates` מהשער | ספריות polling קיימות |
| Push | השער עושה POST webhook פנימי לצרכן | ספריות webhook קיימות |

במצב Push: healthcheck לצרכן כל 60 שניות. כישלון → צבירת תור, לא ניתוק מטלגרם.

### 10.2 ניהול

לא חשוף לאינטרנט. דורש סוד ניהול.

יכולות מינימום:

- יצירה / השהיה / drain / מחיקה של בוט
- הצגת מצב חיבור, עומק תור, דליים, 429 אחרון
- הפעלה/כיבוי paid broadcasts ברמת שער
- בחירת מדיניות תור (`queue` / `reject`)

אין בממשק הניהול שליחת הודעות בשם הבוט מעבר לדיבוג מבוקר.

### 10.3 בריאות

- `/healthz` — התהליך חי
- `/readyz` — אחסון זמין; לא דורש שכל הבוטים `live`

## 11. אינטגרציה לפרויקטים קיימים

המערכת נחשבת משולבת בפרויקט אם ורק אם:

1. הצרכן מצורף לרשת החיצונית או ל־loopback של השער
2. כל קריאות Bot API יוצאות אל השער
3. אין `getUpdates` / `setWebhook` ישירים מול טלגרם מהצרכן
4. ה־compose של הצרכן אינו מגדיר את שירות השער

זה תקף ל־python-telegram-bot, aiogram, grammY, Telegraf, LangBot, או לקוח HTTP גולמי.

## 13. מדדים

לכל בוט:

- מצב סשן
- גיל החיבור לטלגרם
- עומק תור עדכונים וזמן המתנה מקסימלי
- שליחות/שנייה מול תקרת 30
- מספר צ׳אטים פרטיים / קבוצות בדלי ריק
- מונה 429 אמיתי מול 429 מלאכותי
- זמן פריסת צרכן עד שחידוש עיבוד

התראה אם 429 אמיתי > 0 בקצב קבוע, או אם תור עדכונים חוצה סף.

## 14. קריטריוני קבלה

1. `docker compose down` בתיקיית צרכן אינו עוצר את קונטיינר השער ואינו מוחק את הרשת החיצונית.
2. לפחות שני טוקנים חיים במקביל, מבודדים זה מזה.
3. במהלך בניית/החלפת קונטיינר צרכן, עדכונים ממשיכים להיקלט בשער ויוצאים לעיבוד אחרי העלייה, בלי Conflict מטלגרם.
4. שליחה מעל 1/שנייה לאותו משתמש נעצרת או מושהית בשער.
5. שליחה מעל 20/דקה לאותה קבוצה נעצרת או מושהית בשער.
6. שידור מעל 30/שנייה לאותו בוט נעצר או מושהה בשער.
7. `allow_paid_broadcast` אינו מעלה תקרה בלי דגל מפורש בשער.
8. ניתוק צרכן לשתי דקות אינו גורם reconnect מול טלגרם.
9. ריסטארט מבוקר של השער משחזר offset בלי אובדן בעלות על הטוקן.
10. צרכן שפונה ישירות ל־`api.telegram.org` בזמן שהשער פולל נכשל ב־Conflict. זה מאשר בעלות בלעדית.

## 16. גרסאות מוצר

**V1 — חובה**  
ריבוי בוטים, pull+push פנימי, Rate Guard לפי סעיף 8, בידוד לפי סעיף 5, קריטריוני קבלה 1–10.

**V2 — לא חוסם V1**  
צרכנים מרובים לאותו בוט עם lease, Local Bot API כ־upstream בתוך מחזור החיים של השער בלבד, sharding בין מכונות שער.
